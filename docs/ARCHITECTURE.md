# Oculai-Pi architecture

## System boundary

Oculai-Pi is a local-first Windows desktop system. PostgreSQL is the durable
source of truth; the renderer is a presentation client and recent-run JSON is
only a convenience cache.

```text
React renderer (untrusted UI input)
  -> typed preload IPC
Electron main process (trust and orchestration boundary)
  -> Pi AgentSession per run
     -> bounded isolated child AgentSessions
     -> policy-filtered Oculai tools
  -> concurrent ToolBridge (JSONL, timeout, cancellation, restart)
Frozen Python sidecar
  -> deterministic tool registry and domain services
  -> source adapters / HTTP APIs
  -> embedded PostgreSQL 18 + pgvector + pg_trgm
```

The packaged layout is fixed:

- `resources/runtime/python/oculai-sidecar.exe`
- `resources/runtime/postgres/{bin,lib,share}`
- `resources/schema`
- `resources/pi-windows-x64`

Development may resolve Python and PostgreSQL from the active environment;
packaged builds prefer and validate the bundled paths.

## Electron main process

`PiSessionManager` owns one parent `AgentSession` per active run. It creates
child sessions through `SubagentScheduler`, which provides a bounded global
permit pool, per-run cancellation, parallel and sequential-chain modes, and
run/agent-attributed events. Child sessions share the deterministic tool
bridge but have independent prompts and conversation state.

Every LLM tool call passes through a context enforcement layer. It overwrites
`run_id`, `agent_id`, and assessor identity where those fields exist, rejects
cross-run requests, applies enabled-source policy and search concurrency, and
enforces token/turn budgets. Human approval decisions are excluded from every
AgentSession and are callable only through the dedicated renderer-to-main IPC
path.

`ToolBridge` supervises the frozen Python process. It correlates out-of-order
responses by request id, limits active and queued work, sends cancellation
frames, rejects pending work on a crash, and restarts the sidecar. The Python
server dispatches tool coroutines concurrently while serializing stdout writes.

## Durable workflow

Runs follow an explicit persisted state machine:

```text
draft -> running -> paused -> running
                  -> reviewing -> completed
                  -> aborted -> running
```

Completion fails closed: an AgentSession returning is not sufficient. The main
process reloads PostgreSQL task statistics and marks a run complete only when
all durable tasks have succeeded. Otherwise it pauses the run for a real
resume from the stored plan, tasks, candidates, evidence, and review state.

Task execution is a dependency DAG. A task is claimable only when every parent
is `done`. Claims use row locks with `SKIP LOCKED`; completion and failure check
both state and owner. Retry exhaustion becomes terminal on the final allowed
failure. Plan checkpointing validates identifiers, references, duplicates,
cycles, priorities, and retry bounds before creating the plan, tasks,
dependencies, active-plan pointer, and run status in one transaction.

## Evidence and human governance

Evidence tiers are deterministic and shared by assessment code and prompts.
High scores require evidence of the appropriate tier owned by the same run and
candidate. Missing required dimensions fail the gate, and partial dimensions
retain their full-profile weights instead of being renormalized upward.

Sensitive actions use an auditable, single-use approval capability:

```text
request pending approval
  -> trusted human approve/deny (actor, role, notes, timestamp)
  -> action/context/run match
  -> atomic one-time consumption
  -> finalize shortlist or export report
```

The LLM may request and inspect approvals but cannot decide them. The renderer
cannot supply reviewer identity or role; the trusted main process fixes those
fields and the Python domain layer enforces authorization and separation of
duties.

## Database evolution

`oculai-db/schema` is the canonical fresh-install schema. The desktop resource
copy is generated by `scripts/sync_db_schema.py`; CI rejects drift. Forward-only
migrations live under `oculai-db/schema/migrations`, execute transactionally,
and are tracked with SHA-256 checksums so an applied version cannot be silently
rewritten.

The embedded database password is generated on first launch and encrypted with
Electron `safeStorage`. It is never placed in an LLM prompt or renderer payload.
The main process passes database settings only to the sidecar environment.

## Release and verification

The Windows release workflow pins Python, PyInstaller, PostgreSQL, and the exact
pgvector source commit. It builds the sidecar from an exact dependency lock,
bundles third-party licenses, writes a full-file SHA-256 runtime manifest, and
refuses to package missing or changed artifacts.

Installer verification launches the packaged sidecar, checks its ready/tool
contract, and executes a real UTF-8 JSONL capability call. It also uses only
packaged database executables to initialize a disposable cluster, create the
application database, apply every baseline and checksum-tracked migration,
verify `vector` and `pg_trgm`, and stop cleanly. A packaged Electron lifecycle
smoke then verifies renderer load, first and second database starts, sidecar
readiness, graceful shutdown, and the close-during-startup race with zero
residual processes. Lint, types, generated code, schema drift, protocol tests,
database concurrency tests, governance tests, desktop tests, renderer/main
builds, and installer contents are blocking release gates.
